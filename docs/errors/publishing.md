# 記事をブログへ公開したときに起きたこと

この連載の記事を、既存のブログ（Django 製、記事本文は HTML で保存する CMS）へ
Markdown から流し込んだときに実際に手が止まったものの記録です。

KururuCMS 自体のエラーではありませんが、**「別の CMS へ本文を入れる」ときに
何が起きるか**は、この連載で作っているものとそのまま地続きなので残します。

形式は他のファイルと同じく、症状 / 再現条件 / 原因 / 直し方 / 判断方法です。

---

## 1. 日本語の文の途中に、半角スペースが入る

### 症状

記事を表示すると、文の途中に不自然な空白が入る。

```text
カスタムユーザーモデルだけは後から差し替えるのが極端に難しくなります。 理由は「6.
```

「なります。」と「理由は」のあいだに空白がある。Markdown の原文にそんな空白はない。

### 再現条件

原稿を、読みやすさのために40字くらいで折り返して書いている。

```markdown
カスタムユーザーモデルだけは後から差し替えるのが極端に難しくなります。
理由は「6. 内部で起きていること」で説明します。
```

### 原因

**Markdown は段落の中の改行をそのまま HTML に残す。そしてブラウザーは
HTML の改行を「空白」として描画する。**

英語ならこれで正しい。`the quick brown\nfox` は「the quick brown fox」と
表示されてほしいからです。しかし日本語には単語の区切りに空白を置く習慣がないので、
同じ規則が適用されると文の途中に空白が現れます。

つまりこれは変換ライブラリの不具合ではなく、
**HTML の空白の扱いが英語を前提にしている**ことの帰結です。

### 直し方

HTML へ変換する前に、段落内の改行を詰める。ただし全部詰めてはいけません。
英単語どうしの改行では空白が必要だからです。

判定はこうしました。

| 前の行の最後 | 次の行の最初 | どうするか |
| --- | --- | --- |
| ASCII | ASCII | 改行のまま（空白が要る） |
| それ以外 | どちらでも | 詰める（空白は要らない） |
| どちらでも | それ以外 | 詰める（空白は要らない） |

「どちらか一方でも日本語なら詰める」という規則です。
`` `config` `` のようにコードで終わって日本語が続く場合も正しく詰まります。

詰めてはいけない場所もあります。

- コードブロックの中（```` ``` ```` で囲まれた範囲）
- 表の行（`|` で始まる行）
- 見出しの直後
- 箇条書きの**次の項目**（`- ` で始まる行。詰めると2項目が1項目になる）

逆に、箇条書きの**折り返し**（インデントされた続き）は詰めるのが正解です。

### 判断方法

変換後の HTML から `<p>...</p>` を取り出し、
その中に「日本語 → 改行 → 日本語」が何回あるかを数える。
0 に近ければ効いています。

## 2. 「解答」の折りたたみが消えて、答えが丸見えになる

### 症状

各記事の「今日の復習問題」で、解答は `<details>` で畳んでいる。
これがブログに入れると畳まれず、問題文のすぐ下に答えが出てしまった。

### 再現条件

本文を HTML サニタイザー（bleach）に通す CMS へ、
`<details><summary>解答</summary>…</details>` を含む本文を保存する。

### 原因

サニタイザーの許可タグ一覧に `details` と `summary` が入っていなかった。

許可タグ方式（allowlist）は、**知らないタグは危険とみなして落とす**のが仕事なので、
これは設計どおりの動作です。「消された」のではなく「許可していなかった」。

厄介なのは、**bleach の `strip=True` はタグだけ外して中身の文字は残す**ことです。
そのため「エラーも警告も出ず、レイアウトだけ崩れて、答えが露出する」という
気づきにくい壊れ方をします。

### 直し方

`details` と `summary` を許可タグへ追加し、`details` の `open` 属性も許可する。

この2つは JavaScript なしで開閉できる標準要素で、
スクリプトを実行できる属性も子要素も持たないので、許可しても攻撃面は増えません。

同時に、次を固定するテストを書きました。許可タグを増やす変更は、
あとから「なぜ増えたのか」が分からなくなるためです。

- `details` / `summary` が残ること（増やした理由）
- `<script>` は変わらず落ちること（増やしても危なくなっていないこと）
- `ontoggle` のようなイベント属性が落ちること

### 判断方法

保存後の本文に `<details>` が含まれているかを見る。
サニタイザーの前後で文字数を比べると、
どのくらい削られたかがすぐ分かります（今回は記事あたり 63〜80 文字でした）。

## 3. 表に罫線がなく、列の境目が読めない

### 症状

「コードの意味」「コマンドの説明」は表で書いている。
ブログに入れると、罫線も背景色もない文字の羅列になった。

### 再現条件

`.article-content` に表のスタイルが無い CMS へ、表を含む本文を入れる。

### 原因

ブラウザー既定の `<table>` には罫線がありません。
そのブログの既存記事に表がほとんど無かったため、
これまで誰も困らず、スタイルが用意されていませんでした。

### 直し方

`border-collapse: collapse` と `th` / `td` の枠線を足す。
あわせて、**幅の広い表がページ全体を横スクロールさせない**ようにしました。

```css
.article-content table {
    display: block;
    overflow-x: auto;
}
```

これがないと、スマートフォンで本文全体が横に動いてしまいます。

### 判断方法

スマートフォン幅（375px）で開き、**ページ本体が横に動かないこと**と、
表だけが横にスクロールできることを見る。

## 4. 記事どうしのリンクが、書いた時点では作れない

### 症状

記事の「次回予告」から翌日の記事へリンクしたいが、
リンク先の URL が記事の主キー（`/diary/detail/123/`）で決まるため、
記事を作る前は URL が分からない。

### 再現条件

記事 URL が自動採番の ID に依存している CMS へ、相互リンクを含む記事群を入れる。

### 原因

これは不具合ではなく順序の問題です。
「URL を知るには記事が要る」「記事を完成させるには URL が要る」という循環になっています。

### 直し方

2回に分けました。

1. まず全記事を作る（リンク部分は `#DAYLINK-day-03` という仮の形のまま）
2. 主キーが出そろったら、仮の形を実 URL に置き換えて保存し直す

仮の形をわざと `#`（ページ内リンク）にしているのは、
**サニタイザーに消されない**形にしておくためです。

### 判断方法

保存後の本文に `#DAYLINK-` が1つも残っていないことをテストで確かめる。
残っていたら、置き換えが漏れています。

## 5. slug がぶつかると、無関係な記事を上書きしてしまう

### 症状

（起きてはいない。起きうると気づいて防いだもの）

投入コマンドは slug をキーに `update_or_create` する。
公開先のブログには既に500本以上の記事があるので、
slug がたまたま一致すると、**無関係な記事の本文がまるごと置き換わる**。

### 原因

`update_or_create` は「無ければ作る、有れば上書きする」であって、
「有る物が自分のものかどうか」は見ません。

### 直し方

書き込む前に、同じ slug の記事があるかを調べ、
それが**この連載の記事だと分かる印**（本文に含まれる目印のクラス名、
またはタイトルが `【N日目】` で始まること）を持っていなければ、
何も書かずに中止する。

処理全体を1つのトランザクションに入れているので、
途中まで作って止まる状態にもなりません。

### 判断方法

別のタイトルの記事を同じ slug で作っておき、
コマンドが中止すること・その記事の本文が変わっていないことをテストで確かめる。
