# 12日目に実際に起きたエラー

12日目は SSH を鍵認証だけにする回です。
**間違えると自分がサーバーへ入れなくなる**ので、
検証用のコンテナを立て、そこで本物の sshd を相手に確かめながら作りました。

以下は、その過程で実際に踏んだものです。
どれも「動いているように見えた」状態から見つかっています。

---

## 1. `/usr/bin/env: 'bash\r': No such file or directory`

### 症状

コンテナへコピーしたスクリプトが、実行した瞬間に落ちる。

```text
/usr/bin/env: 'bash\r': No such file or directory
```

### 原因

Windows で書き出したファイルの改行が CRLF になっていた。

シェバングは1行目の `#!/usr/bin/env bash` を読みます。
行末に `\r` が付いていると、`bash\r` という名前の実行ファイルを
探しに行き、当然見つかりません。

メッセージに `\r` が見えているので原因は書いてあるのですが、
**エディターの画面上では CRLF も LF も同じに見えます。**
ファイルを何度読み返しても分かりません。

### 直し方

`.gitattributes` で LF に固定しました。

```text
* text=auto eol=lf

*.sh   text eol=lf
*.conf text eol=lf
```

### 判断方法

「気をつける」では再発します。検証スクリプトの**最初の手順**として、
CR が混ざっていないことを機械的に確かめるようにしました。

```bash
if awk '/\r/ { found = 1 } END { exit !found }' "$script"; then
    echo "CR が混ざっています: $script"
    exit 1
fi
```

---

## 2. その CR 検査自身に、CR が入っていた

### 症状

LF のファイルしか無いのに、検査が全件「CR あり」と報告する。

### 原因

検査の書き方が最初はこうでした。

```bash
grep -q $'\r' "$script"
```

この判定を含むスクリプト自体を Windows から書き出したため、
**パターンの中に本物の CR が入りました。**
`$'\r'` という記法ではなく、生の CR 一文字がファイルに書かれた状態です。

結果として、検査は「CR を含む行」ではなく別のものを探し、
常に真を返していました。

### なぜ厄介だったか

1番のエラーを検知するために足した仕組みが、
1番と同じ原因で壊れていました。

しかも**失敗する側に倒れていた**ので、
「検査は動いている」と誤解したまま先へ進むことはありませんでした。
逆に倒れていたら、CR 混入を素通りさせたまま気づけません。

検査を書くときは、**通る場合と落ちる場合の両方**を
一度ずつ確かめる必要があります。

### 直し方

パターンに CR を書かず、`awk` に判定させました。

```bash
awk '/\r/ { found = 1 } END { exit !found }'
```

`\r` は awk が解釈するエスケープなので、
ファイルの中身は ASCII だけで済みます。

## 3. `passwd --lock` した利用者は、鍵でもログインできなくなった

### 症状

11日目で作った `deploy` 利用者が、正しい鍵を持っているのに入れない。

```text
User deploy not allowed because account is locked
```

### 再現条件

11日目の `bootstrap.sh` で `passwd --lock deploy` を実行し、
12日目の設定に `UsePAM no` を書いた。

### 原因

`passwd --lock` は `/etc/shadow` のパスワード欄の先頭に `!` を付けます。
これは「パスワードでは入れない」という意味ですが、
**アカウント全体のロックとしても解釈されます**。

その判定を行うのが PAM です。`UsePAM yes`（sshd の既定）なら、
鍵認証で入った場合は「パスワードは使わないので `!` は無関係」と扱われます。
`UsePAM no` にすると sshd が自分でロック状態を見に行き、
`!` を「このアカウントは使用不可」と読んで拒否します。

### 直し方

`UsePAM no` を書かないことにしました。

`UsePAM yes` は既定値なので、**書かない**のが正しい対応です。
「明示しておいた方が親切だろう」と思って書いた1行が、
締め出しの原因になっていました。

### 判断方法

コンテナで本物の sshd を起動し、実際に鍵でログインする手順を
検証スクリプトへ入れました。設定ファイルを読むだけでは分かりません。

## 4. 「確認できない」を「確認できなかった」と同じ扱いにしていた

### 症状

新しく立てたサーバーで、鍵でログインできているのに
`verify-login.sh` が「ログインした記録がありません」と言って止まる。

### 原因

認証ログを読んで `Accepted publickey for deploy` を探す作りでしたが、
**ログが空だった場合**を「記録が無い」と同じ 1 で返していました。

ログが空になる理由はいくつもあります。

* ログローテーションで直前に流れた
* sshd が別の場所へ記録している
* コンテナで、まだ journald が動いていない

どれも「ログインしていない」という意味ではありません。

### なぜ直す必要があったか

このスクリプトは、12日目の `harden-ssh.sh` が
**実行してよいかを判断する関所**です。

「分からない」を「駄目」に寄せると、入れている人の作業が止まります。
「分からない」を「大丈夫」に寄せると、締め出しを防げません。
どちらにも寄せてはいけないので、第三の返り値が要ります。

### 直し方

終了コードを3つに分けました。

```bash
EXIT_FOUND=0        # 鍵ログインの記録があった
EXIT_NOT_FOUND=1    # 記録が無かった
EXIT_UNKNOWN=2      # 判断できなかった
```

`harden-ssh.sh` は 0 のときだけ進みます。
2 のときは、1 と同じく設定を1文字も書き換えずに終了します。
ただしメッセージは変えてあり、`--log-file` で記録先を指定する案内を出します。

## 5. 設定を巻き戻したつもりが、防御を外していた

### 症状

これは**動作としては正常に見えた**ため、テストを書いていて気づきました。

`harden-ssh.sh` は、書いた設定を `sshd -t` で検査してから反映します。
検査に落ちたときの処理が、最初はこうでした。

```bash
rm -f "$CONF_PATH"
die "sshd の設定に誤りがあったため、書いたファイルを削除しました。"
```

### 何が問題だったか

このスクリプトは**2回目以降も実行されます**。

1回目で `PasswordAuthentication no` が入った状態のサーバーに対し、
2回目の実行が（たとえば `--port` に不正な値を渡して）検査に落ちたとします。

すると `rm -f` は、**1回目に入れた設定ごと**消します。
そして `sshd` を reload しないまま終了するので、その場では何も起きません。

次に何かの理由で sshd が再読み込みされた瞬間、
`PermitRootLogin` も `PasswordAuthentication` も既定値へ戻ります。
**パスワード認証と root ログインが、無言で復活します。**

「設定ミスを安全に弾いた」つもりの処理が、防御を外していました。

### 原因

`write_file` は上書きの前に `.bak-<日時>` として控えを取っています。
消すべきなのは「今書いた新しいファイル」ですが、
`rm` は控えの存在を知らないので、戻すのではなく無くしていました。

### 直し方

直前の控えがあれば、それを戻します。

```bash
previous="$(ls -1t "${CONF_PATH}".bak-* 2>/dev/null | head -1 || true)"
if [ -n "$previous" ]; then
    mv -f "$previous" "$CONF_PATH"
    die "sshd の設定に誤りがあったため、直前の設定へ戻しました（$CONF_PATH）。"
fi
rm -f "$CONF_PATH"
die "sshd の設定に誤りがあったため、書いたファイルを削除しました。"
```

控えが無い場合（＝1回目の実行）は、消すのが正しい動作です。

### 判断方法

検証スクリプトで、次の順に実行しています。

1. 正しい設定で1回実行し、`PasswordAuthentication no` が入ることを確かめる
2. わざと壊れた設定で実行し、失敗することを確かめる
3. **その後で** `PasswordAuthentication no` がまだ残っていることを確かめる

3 が要点です。2 の終了コードだけを見ていると通ってしまいます。
**「失敗したこと」ではなく「失敗した後の状態」を見ます。**
